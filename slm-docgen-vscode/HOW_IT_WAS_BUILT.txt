================================================================================
          HOW THE SLM DOCGEN VS CODE EXTENSION (.vsix) WAS BUILT
================================================================================

This document explains every tool, technology, file, and step involved in
creating the SLM DocGen VS Code extension packaged as a .vsix file.


================================================================================
1. WHAT IS A .vsix FILE?
================================================================================

A .vsix file is a packaged VS Code extension. It's essentially a ZIP archive
containing the compiled extension code, metadata, and assets. You install it
in VS Code with:

    code --install-extension slm-docgen-vscode-0.1.0.vsix

Or via VS Code: Extensions panel → "..." menu → "Install from VSIX..."


================================================================================
2. TOOLS & TECHNOLOGIES USED
================================================================================

Language:       TypeScript (compiled to JavaScript)
Runtime:        Node.js (VS Code extensions run on Node.js)
Bundler:        Webpack (bundles all code into a single dist/extension.js)
Compiler:       ts-loader (Webpack plugin that compiles TypeScript → JavaScript)
Packager:       @vscode/vsce (official tool to create .vsix from the project)
Package Manager: npm (manages all dependencies)

Key Runtime Dependencies:
  - axios (^1.6.5)         → HTTP client for calling the Python backend API
  - form-data (^4.0.0)     → Multipart form encoding for file uploads
  - archiver (^6.0.1)      → Creates ZIP archives for directory documentation

Key Dev Dependencies:
  - typescript (^5.3.3)    → TypeScript compiler
  - webpack (^5.89.0)      → Bundles everything into one file
  - webpack-cli (^5.1.4)   → CLI for running webpack
  - ts-loader (^9.5.1)     → Webpack loader for TypeScript files
  - @types/vscode (^1.85.0)→ Type definitions for VS Code Extension API
  - @types/node (20.x)     → Type definitions for Node.js APIs
  - @types/archiver (^6.0.2)→ Type definitions for archiver
  - @vscode/vsce (^3.9.1)  → Tool to package extensions into .vsix
  - eslint + plugins       → Code linting

================================================================================
4. KEY FILES EXPLAINED
================================================================================

--- package.json ---
The most important file. It tells VS Code:
  - Extension name, version, description, publisher
  - "main": "./dist/extension.js"  → Where the compiled code lives
  - "activationEvents"   → When to load the extension (on Python/Java/JS files)
  - "contributes.commands"→ Commands registered in the Command Palette
  - "contributes.menus"   → Right-click context menu entries
  - "contributes.configuration" → User-configurable settings

--- tsconfig.json ---
Tells TypeScript how to compile:
  - target: ES2020 (modern JavaScript)
  - module: commonjs (Node.js module format)
  - strict: true (all strict type checking enabled)

--- webpack.config.js ---
Bundles all source files and dependencies into one dist/extension.js:
  - target: 'node' (runs in Node.js, not browser)
  - entry: './src/extension.ts'
  - externals: { vscode: 'commonjs vscode' }  → Don't bundle vscode API
  - Uses ts-loader to compile TypeScript during bundling

--- .vscodeignore ---
Excludes unnecessary files from the .vsix:
  - Source TypeScript files (src/)
  - node_modules/
  - Config files
  - Only dist/extension.js, package.json, README.md, LICENSE go in


================================================================================
5. SOURCE CODE ARCHITECTURE
================================================================================

extension.ts (Main Entry Point)
  ├── activate()         → Called when extension loads
  │   ├── Creates OutputChannel for logging
  │   ├── Creates StatusBarManager
  │   ├── Creates ServerManager
  │   ├── Auto-starts Python server if configured
  │   └── Registers all commands
  │
  ├── Commands Registered:
  │   ├── slm-docgen.startServer      → Start the Python backend
  │   ├── slm-docgen.stopServer       → Stop the Python backend
  │   ├── slm-docgen.showLogs         → Show server output
  │   ├── slm-docgen.documentFunction → (Placeholder for cursor-level docs)
  │   ├── slm-docgen.documentFile     → Document the currently open file
  │   ├── slm-docgen.documentWorkspace→ Document entire workspace or pick folder
  │   └── slm-docgen.documentDirectory→ Right-click folder → document it
  │
  ├── collectSourceFiles()  → Recursively finds .py/.java/.js/.ts files
  └── deactivate()          → Cleanup on extension shutdown

ApiClient.ts (HTTP Communication)
  ├── health()          → GET /health (check if server is running)
  ├── info()            → GET /info (server capabilities)
  ├── generateDoc()     → POST /generate/doc (single code snippet)
  ├── generateFile()    → POST /generate/file (single file via multipart)
  └── generateProject() → POST /generate/project (ZIP of entire project)

ServerManager.ts (Python Server Lifecycle)
  ├── start()           → Spawns "python3 cli.py serve ..." as child process
  │                       First tries connecting to an already-running server
  ├── stop()            → Sends SIGTERM to gracefully stop the server
  ├── startHealthChecks()→ Polls /health every 2s until model is loaded
  ├── findSlmDocgenPath()→ Locates slm_docgen directory (settings or auto)
  └── findAdapterPath()  → Locates model adapter files

StatusBar.ts (UI)
  └── Shows server status: Stopped → Starting → Loading Model → Ready


================================================================================
6. HOW THE EXTENSION WORKS (FLOW)
================================================================================

Single File Documentation:
  1. User right-clicks file → "Document Current File"
  2. Extension reads file content from editor
  3. Creates .bak backup in .slm_docgen_backup/ folder
  4. Sends file to Python server via POST /generate/file (multipart upload)
  5. Server runs the fine-tuned Qwen2.5-Coder model on each function/class
  6. Server returns modified source with docstrings injected
  7. Extension replaces the editor content with the documented version

Directory/Workspace Documentation:
  1. User right-clicks folder → "Document This Directory"
     Or Command Palette → "Document Workspace"
  2. Extension recursively collects all supported source files
  3. Creates .bak backups of all files in .slm_docgen_backup/
  4. Zips all files using the archiver library
  5. Sends ZIP to Python server via POST /generate/project
  6. Server processes all files, generates README
  7. Extension writes back all modified files + README_generated.md
  8. Opens the generated README in the editor


================================================================================
7. BUILD & PACKAGE PROCESS (Step by Step)
================================================================================

Step 1: Install dependencies
    cd slm-docgen-vscode
    npm install

Step 2: Compile & bundle with webpack
    npm run package
    → Runs: webpack --mode production --devtool hidden-source-map
    → Compiles TypeScript → JavaScript via ts-loader
    → Bundles everything into dist/extension.js (~597 KB)

Step 3: Package into .vsix
    npx vsce package --allow-missing-repository
    → Runs the prepublish script (npm run package) again
    → Reads package.json for metadata
    → Reads .vscodeignore to know what to exclude
    → Creates slm-docgen-vscode-0.1.0.vsix (~162 KB)

What's inside the .vsix:
    extension/
    ├── package.json           (manifest)
    ├── readme.md              (docs)
    ├── LICENSE.txt             (license)
    └── dist/
        └── extension.js       (all the compiled code)

Step 4: Install the extension
    code --install-extension slm-docgen-vscode-0.1.0.vsix

Or the single combined command:
    npm run build:vsix
    → Runs: npm run package && vsce package


================================================================================
8. HOW THE EXTENSION COMMUNICATES WITH THE PYTHON BACKEND
================================================================================

The extension does NOT run the AI model itself. It communicates with the
slm_docgen FastAPI server over HTTP (localhost:8000).

    VS Code Extension                    Python Backend (FastAPI)
    ─────────────────                    ───────────────────────
    ApiClient.ts                         slm_docgen/app/main.py
        │                                       │
        ├── GET /health      ──────────→  health check endpoint
        ├── POST /generate/file ───────→  processes single file
        ├── POST /generate/project ────→  processes ZIP of project
        │                                       │
        │                               Runs Qwen2.5-Coder model
        │                               with fine-tuned LoRA adapters
        │                                       │
        ←── JSON response ─────────────  returns documented code + README

The extension can either:
  a) Auto-start the server (spawns python3 cli.py serve as a child process)
  b) Connect to an already-running server on the configured port

================================================================================
10. SUMMARY
================================================================================

The extension is a TypeScript project that:
  1. Uses the VS Code Extension API to add commands and context menus
  2. Manages a Python FastAPI server that runs the AI model
  3. Communicates over HTTP (axios) to send code and receive documented code
  4. Uses webpack to bundle everything into a single JavaScript file
  5. Uses vsce to package it into an installable .vsix file

The entire flow: TypeScript source → webpack bundle → vsce package → .vsix file
