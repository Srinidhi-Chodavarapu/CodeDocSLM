PROJECT TITLE
-------------
Automated Multi-Language Code Documentation Generation Using Fine-Tuned Small Language Models with LoRA Adapters


1. PROJECT OVERVIEW
===================

1.1 Purpose
-----------
This project implements an AI-powered code documentation generator that automatically creates high-quality docstrings for Python, Java, and JavaScript/TypeScript code using a fine-tuned Small Language Model (SLM). The system runs entirely locally, ensuring privacy and eliminating cloud dependencies.

1.2 Core Problem
----------------
- Manual code documentation is time-consuming and often inconsistent
- Developers frequently skip documentation, leading to poor code maintainability
- Cloud-based AI solutions raise privacy concerns for proprietary codebases
- Large language models are computationally expensive for routine documentation tasks

1.3 Solution Approach
---------------------
Fine-tune a small, efficient language model (Qwen2.5-Coder-1.5B-Instruct) using QLoRA (Quantized Low-Rank Adaptation) to specialize in generating language-specific docstrings while maintaining local deployment and fast inference.

1.4 Key Innovation
------------------
- Small model, specialized task: 1.5B parameter model vs 70B+ general-purpose models
- Multi-language support: Single model handles Python (Google-style), Java (Javadoc), and JavaScript (JSDoc)
- Production-ready: Complete pipeline from parsing to injection with safety mechanisms
- Resource-efficient: 4-bit quantization enables inference on consumer GPUs


2. TECHNICAL ARCHITECTURE
==========================

2.1 System Components
---------------------

A. Parser Module (slm_docgen/app/parser.py)
--------------------------------------------
Purpose: Extract documentable code units from source files

Technologies:
- Python: AST (Abstract Syntax Tree) parsing
- Java/JavaScript: Regex-based extraction

Output Data Structure:
@dataclass
class CodeUnit:
    name: str              # Function/class/method name
    kind: str              # 'function', 'class', 'method'
    code: str              # Source code snippet
    language: str          # 'python', 'java', 'javascript'
    file_path: str         # File location
    start_line: int        # Start line number
    end_line: int          # End line number
    docstring: Optional[str]      # Existing docstring (if any)
    generated_doc: Optional[str]  # AI-generated documentation
    latency: Optional[float]      # Generation time in seconds

Key Features:
- Skip patterns: __pycache__, .git, node_modules, venv, dist, build
- File limit controls to prevent overloading
- Multi-language extension mapping: .py, .java, .js, .jsx, .ts, .tsx


B. Model Module (slm_docgen/app/model.py)
------------------------------------------
Purpose: Load fine-tuned model and generate documentation

Model Loading Strategy:
1. Primary: Unsloth (optimized, faster inference)
2. Fallback: Transformers + PEFT (standard approach)

System Prompts by Language:
- Python: "Generate accurate, well-structured documentation following Google-style. Include summary, parameter types, and return descriptions."
- Java: "Generate Javadoc-style documentation with @param, @return, and @throws tags."
- JavaScript: "Generate JSDoc-style documentation with @param types and @returns tags."

Inference Configuration:
- Max sequence length: 2048 tokens
- 4-bit quantization enabled by default
- Temperature: Not explicitly set (model default)
- Caching: Global singleton pattern for model/tokenizer


C. Injector Module (slm_docgen/app/injector.py)
------------------------------------------------
Purpose: Insert generated docstrings back into source files

Safety Mechanisms:
- Bottom-up processing: Sorts units by line number in reverse to preserve line positions
- Automatic backups: Creates .bak files before modification
- Indentation preservation: Detects and maintains original code formatting
- Docstring replacement: Handles both insertion and replacement cases

Language-Specific Formatting:
- Python: Triple-quoted strings with proper indentation
- Java: /** ... */ Javadoc blocks
- JavaScript: /** ... */ JSDoc blocks


D. Assembler Module (slm_docgen/app/assembler.py)
--------------------------------------------------
Purpose: Generate comprehensive README.md files

README Sections:
1. Project title with language badges
2. LLM-generated overview paragraph
3. Installation instructions (auto-detected from requirements.txt, package.json)
4. Dependencies listing
5. Project structure tree
6. API reference with collapsible code examples
7. Usage examples

Language Badges:
- Python: ![Python Badge]
- Java: ![Java Badge]
- JavaScript: ![JavaScript Badge]


E. FastAPI Server (slm_docgen/app/main.py)
-------------------------------------------
Purpose: REST API for integration with editors and CI/CD

Endpoints:
- POST /generate-doc: Generate docstring for single code snippet
- POST /generate-file: Process entire file
- POST /generate-project: Process entire project (zip upload)
- GET /health: Health check

Configuration (Environment Variables):

- LOAD_IN_4BIT: Enable 4-bit quantization (default: true)
- MAX_FILES: Maximum files per project (default: 50)
- MAX_ZIP_MB: Maximum upload size (default: 50)

CORS: Enabled for VS Code extension integration

3.3 Processing Pipeline
------------------------
1. Loading: Download from HuggingFace Hub
2. Filtering: Remove low-quality, short, or malformed examples
3. Deduplication: Hash-based deduplication using SHA-256
4. Balancing: Equal representation across Python, Java, JavaScript
5. Formatting: Convert to Qwen2.5 chat template format

-------------------------

You are a Python documentation assistant. [...]<|im_end|>
<|im_start|>user
Generate documentation for this code:
[CODE SNIPPET]<|im_end|>
<|im_start|>assistant
[GENERATED DOCSTRING]<|im_end|>


3.5 Quality Metrics
--------------------
- ROUGE score filtering: Minimum threshold for reference quality
- Length constraints: Min/max token limits
- Syntax validation: Parse code to ensure validity


4. MODEL FINE-TUNING
=====================

4.1 Base Model
--------------
- Name: Qwen2.5-Coder-1.5B-Instruct
- Parameters: 1.5 billion
- Architecture: Qwen2 decoder-only transformer
- Specialization: Pre-trained on code datasets
- Instruction-tuned: Already follows chat templates


4.2 Fine-Tuning Method: QLoRA
------------------------------
QLoRA = Quantized Low-Rank Adaptation

Advantages:
- Memory Efficient: 4-bit quantization reduces VRAM usage by ~4x
- Parameter Efficient: Only train ~0.5% of model parameters
- Quality: Minimal degradation compared to full fine-tuning
- Deployment: Can run on consumer GPUs (16GB VRAM)


4.3 LoRA Configuration (from adapter_config.json)
--------------------------------------------------
{
  "base_model": "unsloth/qwen2.5-coder-1.5b-instruct-bnb-4bit",
  "peft_type": "LORA",
  "task_type": "CAUSAL_LM",
  "r": 16,                    // LoRA rank (matrix dimension)
  "lora_alpha": 32,           // Scaling factor
  "lora_dropout": 0.0,        // No dropout for inference
  "target_modules": [
    "q_proj",                 // Query projection
    "k_proj",                 // Key projection
    "v_proj",                 // Value projection
    "o_proj",                 // Output projection
    "gate_proj",              // Gate projection (MLP)
    "up_proj",                // Up projection (MLP)
    "down_proj"               // Down projection (MLP)
  ],
  "bias": "none",
  "use_dora": false,
  "use_rslora": false
}

Explanation:
- r=16: Low-rank matrices of dimension 16 (trade-off between efficiency and expressiveness)
- alpha=32: 2x scaling amplifies LoRA contribution
- Target Modules: All attention and MLP projections for maximum adaptation

4.5 Hardware & Runtime (from finetune-upgrade.ipynb)
-----------------------------------------------------
- GPU: NVIDIA T4 (16GB VRAM)
- Platform: Kaggle / Google Colab
- Training Time: 9-11 GPU hours
- Framework: Unsloth + TRL (Transformer Reinforcement Learning)
- Optimizer: AdamW (implicit from SFTTrainer)


4.6 Training Process
--------------------
1. Install Unsloth and dependencies
2. Load base model in 4-bit with Unsloth
3. Attach LoRA adapters to target modules
4. Load chat-formatted dataset
5. Configure SFTTrainer with loss masking (train on responses only)
6. Train for 1 epoch with gradient accumulation
7. Save LoRA adapters (only trainable parameters)
8. Run inference test on validation samples


4.7 Output Artifacts
--------------------
- adapter_config.json: LoRA configuration
- adapter_model.safetensors: Trained adapter weights (~64MB)
- tokenizer_config.json: Tokenizer settings
- tokenizer.json: Vocabulary
- chat_template.jinja: Qwen2.5 chat format template
- training_config.json: Hyperparameters and training metadata


5. EVALUATION METRICS (from slm_evaluation.ipynb)
==================================================

5.1 Automatic Metrics
---------------------

A. BLEU-4
---------
- Purpose: Surface-level n-gram overlap
- Range: 0-100 (higher is better)
- Measures: Precision of 1-4 grams against reference
- Limitation: Doesn't capture semantic equivalence

B. ROUGE-L
----------
- Purpose: Recall-oriented longest common subsequence
- Range: 0-1 (higher is better)
- Measures: How much of reference is covered
- Strength: Better for longer text like docstrings

C. BERTScore
------------
- Purpose: Semantic similarity using contextual embeddings
- Range: 0-1 (higher is better)
- Measures: Token-level similarity via BERT
- Strength: Captures paraphrasing and semantic equivalence


5.2 Custom Metrics
------------------

D. Parameter Coverage
---------------------
- Definition: Percentage of function parameters mentioned in generated docstring
- Calculation: (mentioned_params / total_params) * 100
- Purpose: Ensure completeness of documentation

E. Style Accuracy
-----------------
- Definition: Whether generated docstring matches expected style
- Styles: Google (Python), Javadoc (Java), JSDoc (JavaScript)
- Validation: Regex patterns for style markers (@param, Args:, etc.)

F. Hallucination Rate
---------------------
- Definition: Percentage of generated docstrings referencing non-existent identifiers
- Detection: Extract mentioned parameters/variables and check against source code AST
- Critical: Low hallucination = high trustworthiness

G. Latency
----------
- Metrics: p50 (median), p95 (95th percentile)
- Measurement: Time from code input to docstring output
- Target: < 1 second for typical functions on T4 GPU


5.3 Comparison Groups
---------------------
1. Fine-tuned model (your model with LoRA)
2. Base model (Qwen2.5-Coder without fine-tuning)
3. Per-language breakdown (Python vs Java vs JavaScript)
4. Per-style breakdown (Google vs Javadoc vs JSDoc)


5.4 Evaluation Workflow
------------------------
1. Load validation dataset (4,478 samples)
2. Generate docstrings with fine-tuned model
3. Generate docstrings with base model (for comparison)
4. Compute metrics for each sample
5. Aggregate by language and style
6. Statistical significance testing (t-test or Wilcoxon)
